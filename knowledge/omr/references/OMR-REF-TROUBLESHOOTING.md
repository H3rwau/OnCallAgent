# OMR 识别问题排查与证据收集

整理来源为云文档《OMR-智批-问题排查》《考号填涂异常专项分析》及当前 Java 源码、问题台账。历史维护口径和平台保留策略不自动代表当前规则。

## OMR 问题排查先固定请求与业务分支

记录时间范围、环境、实际接口、卡型、引擎来源、识别模式、模板版本、图像类型、错误字段及题号。关联业务日志和引擎日志时核对同一 trace 和同一次请求，不用另一轮成功样本证明本次已修复。

普通扫描、首张校验、人工定位和其他异常恢复的步骤不同。云文档的十步表只用于能力总览，不表示每个请求都执行全部步骤。

## OMR 日志缺失或问题归属不明

先确认日志源、实例、时间范围和检索条件，再检查是否拿到了另一页图片或另一轮请求。日志保留时间取决于实际平台配置，不能把旧文档的“三天”当固定值。

OMR 本身也使用 traceId；不能按“有 traceId 就是智批”归属。接口名、调用链和实际题型比单个标识更可靠。只有链接没有日志正文时，不把链接目标当作已获取证据。

## OMR 错误码与返回结果检查

先区分 Java 扫描级状态、题目级明细、引擎原始 ret、Java DetailErrorStatus 和 Go 多层状态。HTTP 成功、外层 code=0、默认结果对象 errorCode=0 都不能单独证明答案有效。

例如码 20 在 Java ErrorType 中为折角，在 DetailErrorStatus 中为结构错误；通用打分条部分告警仍会继续算分。应同时核对结果非空、置信度、题型规则及错误的最早来源。

## OMR 考号异常排查

将图像定位/裁剪、打印缩放或干扰、考号识别结果、学生关系及业务匹配分开。核对当前工作图坐标、模板首框、行列数与实际网格，不根据“考号异常”直接归因引擎。

案例中的裁窄、加宽或偏移只证明特定样本条件，不能给所有模板统一套值。优先参考 I 类案例与考号/条码源码，再由上游核验名册和学校学科匹配。

## OMR 客观题与打分条排查

客观题先看实际题型、原生答案、最终采样框和 Java 整理规则。未涂占位可能来自更早的整图失败；单选多涂按规则显示符号不必然是漏识别。

打分条应区分长条、短条、NewMode、GeneralScoreBar 及红笔模式。换通用接口需要一起适配分值字段，不能只改 scoreType。先核对原始格子结果，再判断是定位、颜色提取还是业务计分问题。

## OMR 网络或依赖故障不能直接归为算法

OTHER_ERROR、QRCODE_ERROR 或超时可能掩盖图片元信息、文件配置、上传 TLS、服务发现或等待连接等早期失败。按发生顺序定位首因，不能仅通过放大超时、重启服务或修改模板来解释故障。

资源台账与历史命令不是当前状态或操作授权。知识库案例用于提出检查方向，实际动作需依据当前证据及环境权限。

## OMR 排查流程的来源与验证边界

Java：`controller/ImageProcessController.java`、`Service/homework/Correct.java`、`AnswerQuestionItem.java`；主题资料为 `docs/java-service/scan-workflow.md`、`docs/omr-issues` 的分类正文。
