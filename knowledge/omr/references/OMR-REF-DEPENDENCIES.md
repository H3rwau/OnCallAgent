# OMR 外部依赖、部署拓扑与环境定位

本说明提炼自《OMR部署》《OMR现网资源维护》《高教接入OMR现网资源维护》和 Java 依赖资料。保留组件职责与定位方法；机器地址、节点数量、连接凭据和历史发布路径不作为知识正文。

## OMR 图片、模板和校正图依赖

Java 从图片和答题卡模板的 URL/对象名读取内容，依赖文件配置和访问能力；校正后还会上传图片，并把地址写入结果。图片元信息、对象路径解析、文件配置初始化和上传失败都可能阻断后续识别。

文件访问涉及 FileCloudConfigService、OSSFileService 等 Dubbo 依赖。返回 OTHER_ERROR 或 QRCODE_ERROR 时，先沿时间顺序检查文件和上传链路，不直接推断二维码或校正算法故障。

## OMR 配置中心与 ZooKeeper 的职责

配置中心决定运行配置最终值；磁盘文件、旧发布说明与注释不证明实例实际配置。ZooKeeper 提供服务发现地址，Java 使用相应命名空间和能力节点找到 Go 服务。

注册节点存在不证明进程或对应算法就绪；无地址、等待连接、RPC 超时和算法执行错误分开判断。地址核对必须包括业务环境、地域、节点能力及实际实例，不能只看端口。

## OMR Redis、隔离状态与缓存

Java 的崩溃隔离涉及 Redis 与本地缓存。历史源码中 0 为正常、1 为疑似并使用隔离池、2 在适用入口返回 DUMP_ERROR，是否适用取决于隔离配置和入口。

UNAVAILABLE 被映射为引擎崩溃类错误，本身不证明原生算法实际崩溃。不能据名称补造自动状态升级链，也不能通过改 Redis 状态代替查明真实原因。

## OMR 多地域、多业务集群的定位

云文档分别列举了不同地域、主集群、灰度、补偿及辅助能力集群。同一端口可出现在不同业务或地域，端口号不能唯一标识实例；“某集群有多少台”“已停用”“保护状态”都属于带日期的资源快照。

提问或查询日志时先固定业务、环境、地域、角色、实例及时间，再从经过维护的资源台账确认连接信息。历史清单不直接当作当前环境事实。

## OMR 拓扑知识与当前 Agent 日志源的区别

OMR 文档可以指导排查，但不会自动让 Agent 获得该环境的日志访问。需在 oncall.logs.sources 中维护真实日志服务、Project/Logstore 或其他原生资源及只读权限。

没有 OMR 日志映射时应反馈资源缺口，不能自动查询其他业务默认日志库并据此给出 OMR 结论。部署资料中的跳转链接也不等于对应日志正文已获取。
