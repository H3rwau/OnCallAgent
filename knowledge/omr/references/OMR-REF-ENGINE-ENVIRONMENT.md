# OMR Go/cgo 开发环境与引擎包版本匹配

本说明从《OMR引擎封装服务环境配置》提炼可复用的构建和运行知识，并结合 Go 仓库及跨仓库资料校正。旧虚拟机口令、IDE 安装路径和按历史命令直接换库的步骤不作为标准操作。

## OMR Go 与原生库的构建边界

Go 封装使用 cgo 调用 C/C++ 动态库。头文件提供声明，动态库提供实现；CFLAGS 决定编译时的头文件搜索，LDFLAGS 决定链接时的库搜索，运行时还需找到库及其依赖。

Go 构建不会自动把相邻 C++ 仓库重新编译成匹配的库。实际发布包中的头文件、库、配置和模型需与 Go 调用约定一致。

## OMR 编译路径与运行路径分开检查

cgo 的 SRCDIR 相对当前 Go 源文件，不是仓库根目录。同一个包内多个文件的 cgo 配置会共同作用，不能只读某个文件的 include/lib 路径判断整体构建。

LD_LIBRARY_PATH 属于启动时动态库搜索，不会在运行时重新解析头文件或编译源码。某库在 lib 目录存在，也不证明进程实际加载的是它。

## OMR 头文件、协议和动态库一起核验

核对函数签名、参数顺序、结构体布局、图片编码、内存所有权和错误码来源。导出同名 C 符号不能证明 ABI 一致，不能直接用另一分支的库覆盖当前发布包。

已有资料记录二维码旧 proto 与生成代码差异、Common 校正接口 7/8 参数差异，以及 Go 随包库比某个 C++ checkout 多接口的情况。应先定位匹配版本，再制定变更与回归范围。

## OMR Java 客户端与消费应用的发布关系

Java engine-jni 修改后，需要确认消费应用实际使用的 Maven 坐标、解析 JAR 和 WAR；源码编译成功不代表旧应用已加载新逻辑。protobuf 修改也需要同步核对 Java/Go 两端的生成类、handler 和兼容性。

构建成功、文件已发布、进程实际运行和历史日志是不同证据，不用其中一项替代全部核验。

## OMR 引擎就绪与服务注册

Go 服务的注册能力受服务族配置影响；有 HTTP 路由、监听端口或 ZooKeeper 节点，不代表对应算法已初始化。服务注册、进程可达、协议可用和业务结果有效分别检查。

只读排查先检查现有进程、日志和配置。旧文档中的删库、替换旧配置、停启或强制杀进程不能直接作为当前故障的默认修复动作。

## OMR 平台和原生库运行边界

已有随包算法库为 Linux x86-64 ELF。macOS 或其他架构上的源码阅读、Java 编译不等于已验证这些原生库可运行；真实验证需匹配操作系统、架构、动态库依赖及模型资源。

原文的 VirtualBox、旧 Ubuntu 镜像与 GoLand 路径只是历史环境搭建方式，不能视为唯一方案或当前可复现环境。
